>在 C/C++ 开发中，我们无时无刻不在使用库（如 `libc.so`）。但库到底是什么？为什么有的程序体积巨大，有的却很娇小？本篇带你从零手搓动静态库，彻底搞懂它们的区别。

# 一、动静态库

## 1.1 库的本质与分类

**库（Library）**，本质上就是写好的、成熟的、可复用的二进制代码
- **静态库（.a）**：程序在**编译链接**时，把库的代码直接“拷贝”到可执行文件中
- **动态库（.so）**：程序在**运行**时，才去加载库的代码

>**注意**：GCC 编译器默认采用**动态链接**。只有当找不到对应的 `.so` 文件时，才会去找同名的 `.a` 文件

## 1.2 静态库的生成与使用

假设我们有一个自己写的 `my_stdio.c` 和 `my_string.c`，想打包成静态库。
1. **生成目标文件（.o）**：`gcc -c *.c`
2. **打包成静态库**：
```bash
ar -rc libmystdio.a my_stdio.o my_string.o
```
- `ar` 时 GNU 归档工具，`rc` 代表 replace and create。静态库名必须以 `lib` 开头，以 `.a` 结尾。
3. **使用静态库**：
```bash
# 场景1：头文件和库文件安装到系统路径下
gcc main.c -lmystdio

# 场景2：头文件和库文件和我们自己的源文件在同一路径下
gcc main.c -L . -lmymath

# 场景3：头文件和库文件有自己的独立路径
gcc main.c -I(头文件路径) -L(库文件路径) -lmymath
```
- `-L`：指定库路径
- `-I`：指定头文件搜索路径
- `-l`：指定库名
- `-lmystdio`：告诉编译器链接 `libmystdio.a` （去掉 lib 前缀和 .a 后缀），如：`libc.so -> c`
**特点**：生成完可执行程序后，你可以把 `libmystdio.a` 删掉，程序依旧可以正常运行。

## 1.3 动态库的生成与使用

1. **生成动态库**：
```bash
gcc -fPIC -c *.c    # 生成位置无关码
gcc -shared -o libmystdio.so *.o
```
- `-shared`：表示生成共享库
- `-fPIC`：产生位置无关码（Position Independent Code）。这就是动态库能加载到任意内存地址的前提
2. **使用动态库**：
```bash
# 场景1：头文件和库文件安装到系统路径下
gcc main.c -lmystdio

# 场景2：头文件和库文件和自己的源文件在同一路径下
gcc main.c -L. -lmymath # 从左到右搜索 -L 指定的目录

# 场景3：头文件和库文件有自己的独立路径
gcc main.c -I(头文件路径) -L(库文件路径) -lmymath
```
3. **运行时的坑**：
直接运行 `./a.out` 会报错 `cannot open shared object file`。以为你虽然编译时找到了库，但**运行时系统不知道去哪找这个 `.so`**
- **解决方案**：
	1. 把 `.so` 拷贝到系统默认库路径（如 `/usr/lib`）
	2. 向系统共享库路径下建立同名软连接
	3. 设置环境变量：`export LD_LIBRARY_PATH=./`
	4. ldconfig 方案：配置 `/etc/ld.so.conf.d/`，ldconfig 更新
```bash
cat /etc/ld.soconf.d/*.conf
ldconfig # 执行 ldconfig，重新加载库搜索路径
```

# 二、目标文件与 ELF 格式：合并

我们写的 `.c` 文件经过 `gcc -c` 编译后，会生成一个 `.o` 文件（目标文件）
在 Linux 下，`.o` 文件、可执行文件 `a.out`、动态库 `.so`，本质都是同一个格式：**ELF（Executable and Linkable Format）**

一个 ELF 文件由四部分组成：
1. **ELF 头（ELF header）**：位于最开头，记录文件类型、机器架构、**入口地址**等，用于定位其他部分
2. **节头表（Section header table）**：**链接视图**。将文件按功能划分为一个个“节“（Section）
3. **程序头表（Program header table）**：**执行试图**。告诉操作系统如何加载文件，将多个”节“合并为“段”（Segment）
4. **数据区**：具体的代码和数据

![](图片/ELF组成.png)

## 2.1 核心的 Section（节）

使用 `readelf` 命令，可查看 `ELF` 文件的 `Section`
- `.text` ：存放机器指令（代码）
- `.data`：已初始化的全局变量和静态变量
- `.bss`：未初始化的全局变量和静态变量（不占磁盘空间，加载时清零）
- `.rodata`：只读数据，如字符串常量
- `.symtab`：符号表。记录源码里的函数名、变量名和代码的对应关系
- `.rela.text`：重定位表。记录那些编译时找不到地址的符号（比如外部函数）
- `.got.plt`（全局偏移表）：`.got` 节保持了全局偏移表。`.got` 节和 `.plt` 节一起提供了对导入的共享函数的访问入口，由动态链接器在运行时进行修改

## 2.2 为什么要区分 Section 和 Segment

- **链接时（Section）**：链接器需要把不同 `.o` 文件的 `.text` 拼在一起，`.data` 拼在一起，所以划分很细
- **加载时（Segment）**：为了减少内存碎片，节省内存页，加载器会把具有相同属性（如可读、可执行）的 Section 合并成一个大 Segment。例如把 `.text` 和 `.rodata` 合并成只读代码段  （READ ONLY），把 `.data` 和 `.bss` 合并成读写数据段（READ & WRITE）

![](图片/屏幕截图%202026-11-09%20113515.png)

>[!note] 为什么要将 section 合并成 segment
>- Section 合并的主要原因时为了减少页面碎片，提高内存使用效率。如果不进行合并，假设页面大小为 4096 字节（内存块基本大小，加载，管理的基本单位）。如果 .text 为 4096 字节，.init 为 512 字节，那么将占用 3 个页面。合并后只需要 2 个页面
>- 此外，操作系统在加载程序时，会将具有相同属性的 section 合并成一个大的 segment，这样就可以实现不同的访问权限，从而优化内存管理和权限访问控制

## 2.3 程序头表（Program header table）与节头表（Section header table）

![](图片/程序头表和节头表的作用%201.png)

- **链接视图（Linking view）**- 节头表 `Section header table`
	- 文件结构的粒度更细，将文件按功能模块的差异进行划分，静态链接分析的时候一般关注的时链接视图，能够理解 ELF 文件中包含的各个部分的信息
	- 为了空间布局上的效率，将来在链接目标文件时，链接器会把很多节（section）合并，规整成可执行的段（Segment）、可读写的段、只读段等。合并了后，空间利用率就高了，否则，许多很小的段会把浪费物理内存页（物理内存页分配一般都是整数倍，4K），所以，链接器趁着链接就把小块合并
- **执行视图（execution view）**- 程序头表 `Program header table`
	- 告诉操作系统，如何加载可执行文件，完成进程内存的初始化。一个可执行程序的格式中，一定有 `program header table`
- 节头表：连接时作用；程序头表：运行加载时作用

# 三、静态链接：地址修补

当我们有多个 `.o` 文件时，它们互相不知道对方存在的。

如果你用 `objdump -d code.o` 反汇编目标文件，你会发现调用外部函数（如 `printf` 或另一个文件里的 `run`）的 `call` 指令，后面的地址**全是 0**！

```bash

	14: 90 nop  
	15: 5d pop %rbp  
	16: c3 retq


$ objdump -d hello.o

hello.o: file format elf64-x86-64  


Disassembly of section .text:  

0000000000000000 <main>:  
	0: f3 0f 1e fa endbr64  
	4: 55 push %rbp  
	5: 48 89 e5 mov %rsp,%rbp  
	8: 48 8d 3d 00 00 00 00 lea 0x0(%rip),%rdi # f<main+0xf>  
	f: e8 00 00 00 00 callq 14 <main+0x14>  # 地址全零
	14: b8 00 00 00 00 mov $0x0,%eax
	19: e8 00 00 00 00 callq 1e <main+0x1e> # 地址全零
	1e: b8 00 00 00 00 mov $0x0,%eax
	23: 5d pop %rbp  
	24: c3 retq
```

- `objdump -d` 命令：将代码段（.text）进行反汇编查看
- `hello.o` 中的 `main` 函数不认识 `printf` 和 `run` 函数
```bash
$ cat hello.c
#include<stdio.h>

void run();

int main()
{
	printf("hello world!\n"):
	run();
	return 0;
}
```
- `code.o` 不认识 `printf` 函数
```bash
$ cat code.c
#include<stdio.h>
void run()
{
	printf("running...\n");
}
```

为什么全是 **0**？因为编译器在编译 `hello.c` 是，根本不知道 `run` 函数会在哪里，所以只能先填 0。同时，在 `.data` 段里留了一个**重定位表**，这张表将来在链接时，就会根据表里的记录的地址将其修正

## 3.1 链接器（Linker）的工作

**静态链接的本质，就是把所有的 `.o` 文件进行合并，并进行地址重定位**

1. **合并段**：把所有 `.o` 的 `.text` 合并成最终的 `.text`，`.data` 合并成最终的 `.data`。合并后，每一个函数的相对位置就确定了，从而计算出最终的**绝对虚拟地址**
2. **修补地址**：链接器拿着重定位表，找到那些填 0 的 `call` 指令，把它们替换成刚刚计算出的正确虚拟地址

**结论**：静态链接生成的程序，在**编译时**就已经把所有的代码的地址写死了。所以它不需要动态链接器，直接把可执行文件扔进内存就能跑。这就是为什么它的体积大，但运行快。

# 四、动态链接

## 4.1 动态链接概要

动态链接的核心思想是：**将链接过程推迟到程序运行时**

这就带来了一个致命的问题：既然动态库是运行时加载的，每次加载到的内存地址可能不一样，那程序了的 `call` 指令怎么去调用库函数呢？如果能随便改，代码段是只读的，怎么改？

## 4.2可执行程序被编译器动了手脚

在 C/C++ 程序中，当程序开始执行时，首先并不会直接跳到 `main` 函数。实际上，程序的入口点是 `_start`，这是一个由 C 运行时库（通常是 glibc）或链接器提供的特殊函数

在 `_start` 函数中，会执行一系列初始化操作：
1. **设置堆栈**：为程序创建一个初始的堆栈环境
2. **初始化数据段**：将程序的数据段（如全局变量和静态变量）从初始化数据复制到相应的内存位置，并清零未初始化的数据段
3. **动态链接（关键）**：`_start` 函数调用动态链接器的代码来解析和加载程序所依赖的动态库（shared libraries）。动态链接器会处理所有的符号解析和重定位，确保程序中的函数调用和变量访问能够正确地映射到动态库中的实际地址
4. **调用 `__libc_start_main`**：动态链接完成，`_start` 函数会调用 `__libc_start_main`（这是 glibc 提供的一个函数）。`__libc_start_main` 函数负责执行一些额外的初始化工作（工作：设置信号处理函数、初始化线程库等）
5. **调用 `main` 函数**：最后， `__libc__start_main` 函数会调用程序的 `main` 函数，此时程序的执行控制权才正式交给用户编写的代码
6. **处理 `main` 函数的返回值**：当 `main` 函数返回时，`__libc_start_main` 会处理返回值，并最终调用 `_exit` 函数来终止程序
> [!note] 什么是动态链接器？
> - 动态链接器（如 ld-linux.so）负责在程序运行时加载动态库
> - 当程序启动时，动态链接器会解析程序中的动态库依赖，并加载这些库到内存中。
> 环境变量和配置文件：
> - Linux 系统通过环境变量（如 LD_LIBRARY_PATH）和配置文件（如 /etc/ld.so.conf 及其子配置文件）来指定动态库的搜索路径
> - 这些路径会被动态链接器在加载动态库时搜索
> 缓存文件：
> - 为了提高动态库的加载效率, Linux 系统会维护一个名为 /etc/ld.so.cache 的缓存文件
> - 该文件包含了系统中所有已知动态库和相关信息，动态链接器在加载动态库时会首先搜索这个缓存文件

## 4.3 动态库中的相对地址

动态库为了随时进行加载和支持并映射到任意进程的任意位置，对动态库中采用相对编址的方案进行统一编址（其实可执行程序也一样，都要遵守平坦模式，只不过 exe 是直接加载的）

```bash
# ubuntu下查看任意⼀个库的反汇编
objdump -S /lib/x86_64-linux-gnu/libc-2.31.so | less

# Cetnos下查看任意⼀个库的反汇编
$ objdump -S /lib64/libc-2.17.so | less
```

## 4.4 程序与库的关系

### 1. 程序与库的映射

动态库也是一个文件，程序只能访问加载到内存里的动态库
只要是文件，都能进行文件操作。不过我们访问库函数，是通过虚拟地址进行跳转访问的，所以需要把动态库映射到进程的地址空间中

### 2. 程序如何调用库函数？

>[!warning] 注意：
>- 库已经被我们映射到了当前进程的地址空间中
>- 库的虚拟起始地址我们也已经知道了
>- 库中每一个方法的偏移量地址我们也知道了
>- 访问库中任意方法，只需要知道**库的起始虚拟地址+方法偏移量**即可定位库中的方法
>- 整个调用过程，是从代码区跳转到共享区，调用完毕在返回到代码区，整个过程完全在进程地址空间中进行的

![](图片/程序如何调用库函数.png)

### 3. 全局偏移表 GOT（global offset table）

>[!warning] 注意：
>- 我们的程序运行之前，先把所以库加载并映射，就已经知道所有库的起始虚拟地址
>- 然后对我们加载到内存里的程序中的库函数调用的地址进行修改，在内存中二次完成地址设置（加载地址重定位）
>- 代码区在进程中属于只读。采取了全局偏移表 GOT 进行修改：在 `.data（可读可写）` （可执行程序或者库）中专门预留了一片区域用来存放函数的跳转地址，表中每一项都是本运行模块要引用的一个全局变量或函数的地址

![](图片/GOT表动态链接.png)

动态链接采用了 **PIC（地址无关码）**+ **PLT（过程链接表）** + **GOT（全局偏移表）** 的技术

| 表         | 位置         | 记录什么                                                                         |
| --------- | ---------- | ---------------------------------------------------------------------------- |
| **PIC**   | 相对编址 + GOT | 不知道库函数在哪，那代码段里的 `call` 指令**不写绝对地址**，而是使用**相对寻址**（相当于当前指令偏移多少）                |
| **PLT**   | 代码段        | 一小桩代码，负责“跳去 GOT 取地址，然后跳去执行“                                                  |
| **GOT 表** | 数据段        | 在可执行文件的 `.data` 段（可读可写）专门留出一片区域叫 GOT。里面存放的是**库函数在共享区的真实绝对虚拟地址**（运行时由动态链接器填好） |
>PLT 是跳板代码 `jmp *GOT[n]`
>GOT 记录某个具体函数在共享区的真实绝对地址
>PLT -> GOT -> 共享区

```text
1. call printf
   ↓ 编译器把这条 call 编译成 call printf@plt
2. 跳到 PLT 中 printf 对应的桩代码（还在代码段）
   ↓ PLT 桩代码执行：jmp *GOT[printf]   （去 GOT 表取地址）
3. 读 GOT[printf] 里存的地址
   ↓ 这个地址是动态链接器填好的、printf 在共享区的真实虚拟地址
4. 跳到共享区里真正的 printf 代码执行
```

**运作流程**：
1. 程序加载时，动态链接器（`ld-linux.so`）把 `libc.so` 加载到进程的共享区
2. 链接器知道 `printf` 在库里的偏移量，加上库加载的起始地址，算出 `printf` 的真实地址，**填入 GOT 表**
3. 程序执行到 `call printf` 时，先通过相对偏移找到 GOT 表，从表里读出真实的 `printf` 地址，然后跳转过去执行

>[!tip] **延迟绑定（PLT）**：GOT 表是什么时候被填的？
>- 程序刚加载时，`GOT[printf]` 里填的不是 `printf` 的真实地址，而是 PLT 里一段”解析桩“（resolver）的地址
>- **第一次**调用 `printf`：跳到 PLT -> 读 GOT -> 发现是解析桩 -> 解析桩去查动态符号表，算出 printf 真实地址，**回填 `GOT[printf]`**，然后再跳去执行
>- **第二次及以后**：PLT -> 读 GOT -> 直接就是真实地址 -> 直接跳，不再解析
>这就是为什么 GOT 必须放在**可写的数据段**（.got.plt）：它运行时会被动态链接器修改

总而言之，动态链接实际上将链接的整个过程，比如符号查询、地址的重定位从编译时推迟到程序的运行时，它虽然牺牲了一定的性能和程序加载时间。但能够更有效利用磁盘空间和内存资源，极大方便了代码的更新和维护，更关键的是，实现了二进制级别的代码复用

### 4. 动态库在内存中的映射

结合之前的进程地址空间：
1. 可执行文件 `a.out` 被映射到进程的**代码区/数据区**
2. 动态库 `.so` 其实也是一个文件。OS 会在进程的**共享区（mmap区）** 分配一块虚拟内存
3. 通过页表，把 `.so` 文件的代码段映射到物理内存
4. **共享**：如果有第二个进程也用了这个 `.so`，OS 只需要把第二个进程的页表也指向同一块物理内存即可。这就是动态库节省内存的原理

1. `exevce` 系统调用读取 ELF 头，检查魔数（Magic Number）
