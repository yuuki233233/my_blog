# 目标文件与 ELF 格式：合并

我们写的 `.c` 文件经过 `gcc -c` 编译后，会生成一个 `.o` 文件（目标文件）
在 Linux 下，`.o` 文件、可执行文件 `a.out`、动态库 `.so`，本质都是同一个格式：**ELF（Executable and Linkable Format）**

一个 ELF 文件由四部分组成：
1. **ELF 头（ELF header）**：位于最开头，记录文件类型、机器架构、**入口地址**等，用于定位其他部分
2. **节头表（Section header table）**：**链接视图**。将文件按功能划分为一个个“节“（Section）
3. **程序头表（Program header table）**：**执行试图**。告诉操作系统如何加载文件，将多个”节“合并为“段”（Segment）
4. **数据区**：具体的代码和数据

### 核心的 Section（节）

使用 `readelf` 命令，可查看 `ELF` 文件的 `Section`
- `.text` ：存放机器指令（代码）
- `.data`：已初始化的全局变量和静态变量
- `.bss`：未初始化的全局变量和静态变量（不占磁盘空间，加载时清零）
- `.rodata`：只读数据，如字符串常量
- `.symtab`：符号表。记录源码里的函数名、变量名和代码的对应关系
- `.rela.text`：重定位表。记录那些编译时找不到地址的符号（比如外部函数）
- `.got.plt`（全局偏移表）：`.got` 节保持了全局偏移表。`.got` 节和 `.plt` 节一起提供了对导入的共享函数的访问入口，由动态链接器在运行时进行修改

### 为什么要区分 Section 和 Segment

- **链接时（Section）**：链接器需要把不同 `.o` 文件的 `.text` 拼在一起，`.data` 拼在一起，所以划分很细
- **加载时（Segment）**：为了减少内存碎片，节省内存页，加载器会把具有相同属性（如可读、可执行）的 Section 合并成一个大 Segment。例如把 `.text` 和 `.rodata` 合并成只读代码段  （READ ONLY），把 `.data` 和 `.bss` 合并成读写数据段（READ & WRITE）

![](图片/屏幕截图%202026-11-09%20113515.png)

>[!note] 为什么要将 section 合并成 segment
>- Section 合并的主要原因时为了减少页面碎片，提高内存使用效率。如果不进行合并，假设页面大小为 4096 字节（内存块基本大小，加载，管理的基本单位）。如果 .text 为 4096 字节，.init 为 512 字节，那么将占用 3 个页面。合并后只需要 2 个页面
>- 此外，操作系统在加载程序时，会将具有相同属性的 section 合并成一个大的 segment，这样就可以实现不同的访问权限，从而优化内存管理和权限访问控制

### 程序头表（Program header table）与节头表（Section header table）

![](图片/程序头表和节头表的作用%201.png)

- **链接视图（Linking view）**- 节头表 `Section header table`
	- 文件结构的粒度更细，将文件按功能模块的差异进行划分，静态链接分析的时候一般关注的时链接视图，能够理解 ELF 文件中包含的各个部分的信息
	- 为了空间布局上的效率，将来在链接目标文件时，链接器会把很多节（section）合并，规整成可执行的段（Segment）、可读写的段、只读段等。合并了后，空间利用率就高了，否则，许多很小的段会把浪费物理内存页（物理内存页分配一般都是整数倍，4K），所以，链接器趁着链接就把小块合并
- **执行视图（execution view）**- 程序头表 `Program header table`
	- 告诉操作系统，如何加载可执行文件，完成进程内存的初始化。一个可执行程序的格式中，一定有 `program header table`
- 节头表：连接时作用；程序头表：运行加载时作用
