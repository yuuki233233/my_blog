# 动态链接：运行时共享与 GOT 表

动态链接的核心思想是：**将链接过程推迟到程序运行时**

这就带来了一个致命的问题：既然动态库是运行时加载的，每次加载到的内存地址可能不一样，那程序了的 `call` 指令怎么去调用库函数呢？如果能随便改，代码段是只读的，怎么改？

### 动态链接的绝妙设计：GOT 表

动态链接采用了 **PIC（位置无关码）**+ **GOT（全局偏移表）** 的技术
- **PIC**：既然不知道库函数在哪，那代码段里的 `call` 指令**不写绝对地址**，而是使用**相对寻址**（相当于当前指令偏移多少）
- **GOT 表**：在可执行文件的 `.data` 段（可读可写）专门留出一片区域叫 GOT（Global Offset Table）。里面存放的是库函数的**绝对真实地址**

**运作流程**：
1. 程序加载时，动态链接器（`ld-linux.so`）把 `libc.so` 加载到进程的共享区
2. 链接器知道 `printf` 在库里的偏移量，加上库加载的起始地址，算出 `printf` 的真实地址，**填入 GOT 表**
3. 程序执行到 `call printf` 时，先通过相对偏移找到 GOT 表，从表里读出真实的 `printf` 地址，然后跳转过去执行

>[!tip] **延迟绑定（PLT）**：为了进一步加速，动态链接器不会一次性填满所有的 GOT 表。第一次调用 `printf` 时，GOT 表里填的是 PLT 桩代码的地址，桩代码会去找真实地址并更新 GOT 表。第二次调用时，直接跳转。这就是 PLT（过程链接表）的作用


### 动态库在内存中的映射

结合之前的进程地址空间：
1. 可执行文件 `a.out` 被映射到进程的**代码区/数据区**
2. 动态库 `.so` 其实也是一个文件。OS 会在进程的**共享区（mmap区）** 分配一块虚拟内存
3. 通过页表，把 `.so` 文件的代码段映射到物理内存
4. **共享**：如果有第二个进程也用了这个 `.so`，OS 只需要把第二个进程的页表也指向同一块物理内存即可。这就是动态库节省内存的原理

### ELF 加载的全过程

1. `exevce` 系统调用读取 ELF 头，检查魔数（Magic Number）
2. 根据程序头表（Program Header Table），把各个 Sagment 映射到进程的虚拟地址空间
3. 如果发现需要动态链接（有 `.interp` 段），启动动态链接器 `ld-liunx.so`
4. 动态链接器解析依赖，加载所有需要的 `.so` 到共享区，并修改 GOT 表
5. 一切就绪，跳转到 ELF 头中记录的 `Entry point` （`_start` 函数），开始执行用户代码
