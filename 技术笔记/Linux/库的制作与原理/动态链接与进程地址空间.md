# 动态链接

### 动态链接概要

动态链接的核心思想是：**将链接过程推迟到程序运行时**

这就带来了一个致命的问题：既然动态库是运行时加载的，每次加载到的内存地址可能不一样，那程序了的 `call` 指令怎么去调用库函数呢？如果能随便改，代码段是只读的，怎么改？

### 可执行程序被编译器动了手脚

在 C/C++ 程序中，当程序开始执行时，首先并不会直接跳到 `main` 函数。实际上，程序的入口点是 `_start`，这是一个由 C 运行时库（通常是 glibc）或链接器提供的特殊函数

在 `_start` 函数中，会执行一系列初始化操作：
1. **设置堆栈**：为程序创建一个初始的堆栈环境
2. **初始化数据段**：将程序的数据段（如全局变量和静态变量）从初始化数据复制到相应的内存位置，并清零未初始化的数据段
3. **动态链接（关键）**：`_start` 函数调用动态链接器的代码来解析和加载程序所依赖的动态库（shared libraries）。动态链接器会处理所有的符号解析和重定位，确保程序中的函数调用和变量访问能够正确地映射到动态库中的实际地址
4. **调用 `__libc_start_main`**：动态链接完成，`_start` 函数会调用 `__libc_start_main`（这是 glibc 提供的一个函数）。`__libc_start_main` 函数负责执行一些额外的初始化工作（工作：设置信号处理函数、初始化线程库等）
5. **调用 `main` 函数**：最后， `__libc__start_main` 函数会调用程序的 `main` 函数，此时程序的执行控制权才正式交给用户编写的代码
6. **处理 `main` 函数的返回值**：当 `main` 函数返回时，`__libc_start_main` 会处理返回值，并最终调用 `_exit` 函数来终止程序
> [!note] 什么是动态链接器？
> - 动态链接器（如 ld-linux.so）负责在程序运行时加载动态库
> - 当程序启动时，动态链接器会解析程序中的动态库依赖，并加载这些库到内存中。
> 环境变量和配置文件：
> - Linux 系统通过环境变量（如 LD_LIBRARY_PATH）和配置文件（如 /etc/ld.so.conf 及其子配置文件）来指定动态库的搜索路径
> - 这些路径会被动态链接器在加载动态库时搜索
> 缓存文件：
> - 为了提高动态库的加载效率, Linux 系统会维护一个名为 /etc/ld.so.cache 的缓存文件
> - 该文件包含了系统中所有已知动态库和相关信息，动态链接器在加载动态库时会首先搜索这个缓存文件

### 动态库中的相对地址

动态库为了随时进行加载和支持并映射到任意进程的任意位置，对动态库中采用相对编址的方案进行统一编址（其实可执行程序也一样，都要遵守平坦模式，只不过 exe 是直接加载的）

```bash
# ubuntu下查看任意⼀个库的反汇编
objdump -S /lib/x86_64-linux-gnu/libc-2.31.so | less

# Cetnos下查看任意⼀个库的反汇编
$ objdump -S /lib64/libc-2.17.so | less
```

## 程序与库的关系

### 程序与库的映射

动态库也是一个文件，程序只能访问加载到内存里的动态库
只要是文件，都能进行文件操作。不过我们访问库函数，是通过虚拟地址进行跳转访问的，所以需要把动态库映射到进程的地址空间中

### 程序如何调用库函数？

>[!warning] 注意：
>- 库已经被我们映射到了当前进程的地址空间中
>- 库的虚拟起始地址我们也已经知道了
>- 库中每一个方法的偏移量地址我们也知道了
>- 访问库中任意方法，只需要知道**库的起始虚拟地址+方法偏移量**即可定位库中的方法
>- 整个调用过程，是从代码区跳转到共享区，调用完毕在返回到代码区，整个过程完全在进程地址空间中进行的

### 全局偏移表 GOT（global offset table）

>[!warning] 注意：
>- 我们的程序运行之前，先把所以库加载并映射，就已经知道所有库的起始虚拟地址
>- 然后对我们加载到内存里的程序中的库函数调用的地址进行修改，在内存中二次完成地址设置（加载地址重定位）
>- 

动态链接采用了 **PIC（位置无关码）**+ **GOT（全局偏移表）** 的技术
- **PIC**：既然不知道库函数在哪，那代码段里的 `call` 指令**不写绝对地址**，而是使用**相对寻址**（相当于当前指令偏移多少）
- **GOT 表**：在可执行文件的 `.data` 段（可读可写）专门留出一片区域叫 GOT（Global Offset Table）。里面存放的是库函数的**绝对真实地址**

**运作流程**：
1. 程序加载时，动态链接器（`ld-linux.so`）把 `libc.so` 加载到进程的共享区
2. 链接器知道 `printf` 在库里的偏移量，加上库加载的起始地址，算出 `printf` 的真实地址，**填入 GOT 表**
3. 程序执行到 `call printf` 时，先通过相对偏移找到 GOT 表，从表里读出真实的 `printf` 地址，然后跳转过去执行

>[!tip] **延迟绑定（PLT）**：为了进一步加速，动态链接器不会一次性填满所有的 GOT 表。第一次调用 `printf` 时，GOT 表里填的是 PLT 桩代码的地址，桩代码会去找真实地址并更新 GOT 表。第二次调用时，直接跳转。这就是 PLT（过程链接表）的作用


### 动态库在内存中的映射

结合之前的进程地址空间：
1. 可执行文件 `a.out` 被映射到进程的**代码区/数据区**
2. 动态库 `.so` 其实也是一个文件。OS 会在进程的**共享区（mmap区）** 分配一块虚拟内存
3. 通过页表，把 `.so` 文件的代码段映射到物理内存
4. **共享**：如果有第二个进程也用了这个 `.so`，OS 只需要把第二个进程的页表也指向同一块物理内存即可。这就是动态库节省内存的原理

### ELF 加载的全过程

1. `exevce` 系统调用读取 ELF 头，检查魔数（Magic Number）
2. 根据程序头表（Program Header Table），把各个 Sagment 映射到进程的虚拟地址空间
3. 如果发现需要动态链接（有 `.interp` 段），启动动态链接器 `ld-liunx.so`
4. 动态链接器解析依赖，加载所有需要的 `.so` 到共享区，并修改 GOT 表
5. 一切就绪，跳转到 ELF 头中记录的 `Entry point` （`_start` 函数），开始执行用户代码
