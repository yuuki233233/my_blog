# 1. Linux 软件安装三种方式

在 Linux 下，我们一般有三种装软件的方式：

| 方式              | 优点               | 缺点                | 推荐场景       |
| --------------- | ---------------- | ----------------- | ---------- |
| 包管理器（yum/apt）   | 自动解决依赖、版本兼容、卸载干净 | 软件版本可能较旧、需要配置镜像加速 | 服务器、日常开发首选 |
| 源码编译安装          | 最新版本、可自定义优化参数    | 依赖手动解决、编译耗时、卸载麻烦  | 需要最新版或特殊优化 |
| 二进制包（.deb/.rpm） | 安装快、免编译          | 依赖问题、可能污染系统       | 官方不提供包时应急  |

- 二进制包本质就是把编译好的可执行文件、库、配置文件、手册页等，按标准路径 `（/usr/bin、/usr/lib、/etc、/usr/share/man）` 直接解压/拷贝过去，所以叫`“安装 = 拷贝资源”`
- **包管理器是服务器/日常使用首选**，因为它把“下载 → 依赖检查 → 安装 → 注册服务 → 更新源”全部自动化了。 在 Ubuntu/Debian 系上，最常用的是 **apt**（底层是 dpkg）。
> **为什么首选包管理器？**
> 软件的依赖关系非常复杂（A 依赖 B，B 又依赖 C 的某个版本）。包管理器把“下载 → 依赖检查 → 安装 → 配置”全部自动化了，这就是它的核心价值。

### 1.1 apt 常用命令速查

| 命令                          | 作用              | 示例                              |
| --------------------------- | --------------- | ------------------------------- |
| `sudo apt update`           | 更新软件源索引（装软件前必做） | 每次换源或想获取最新包列表时运行                |
| `sudo apt upgrade`          | 升级所有已安装的软件      | 保持系统最新，推荐定期运行                   |
| `sudo apt install 软件名`      | 安装软件（自动解决依赖）    | `sudo apt install vim git curl` |
| `sudo apt remove 软件名`       | 卸载软件（保留配置文件）    | `sudo apt remove nginx`         |
| `sudo apt purge 软件名`        | 彻底卸载（连配置文件一起删）  | `sudo apt purge nginx`          |
| `sudo apt autoremove`       | 自动清理不再需要的孤立依赖包  | 卸载软件后运行，释放空间                    |
| `sudo apt search 关键词`       | 搜索软件包           | `sudo apt search python3-pip`   |
| `sudo apt list --installed` | 列出已安装软件         | 查看系统中装了哪些包                      |

### 1.2 换国内镜源（加速）
国外官方源在国内极其慢，建议换成国内源（如阿里云、清华源）：
```bash
# 1. 备份原文件
sudo cp /etc/apt/sources.list /etc/apt/sources.list.bak

# 2. 一键替换为阿里云源（以 Ubuntu 为例）
sudo sed -i 's/archive.ubuntu.com/mirrors.aliyun.com/g' /etc/apt/sources.list
sudo sed -i 's/security.ubuntu.com/mirrors.aliyun.com/g' /etc/apt/sources.list

# 3. 更新索引生效
sudo apt update
```

**小技巧**：换源后如果报错，先运行 `sudo apt update --fix-missing` 修复

# 2. 代码编辑器 vim
Vim 是 Linux 下的神器，它的核心逻辑是**多模式编辑**。新手只需要掌握三种模式即可：
- **命令模式（Normal）**：默认模式，用于移动光标、复制、删除
- **插入模式（Insert）**：用于打字输入
- **底行模式（Last-line）**：用于保存、退出、替换

>**模式转换规则**：无论你在哪个模式，狂按 `Esc` 键就能回到**命令模式**
>命令模式可以转成其他模式，其他模式只能转回命令模式

## 2.1 常用操作

- `i`：在光标前插入
- `a`：在光标后插入

# 3. 编译器 GCC/G++：代码是如何变成程序的？

## 3.1 编译器处理代码过程

我们写的 `.c` 文件只是一堆文本，机器根本看不懂。GCC 把它变成可执行文件，需要经历 **4 个阶段**：

1. **预处理（-E）**：展开头文件、宏替换、去注释。生成 `.i` 文件。
2. **编译（-S）**：把 C 代码翻译成汇编语言。生成 `.s` 文件。
3. **汇编（-c）**：把汇编翻译成机器能懂的二进制代码。生成 `.o` 目标文件。
4. **链接**：把多个 `.o` 文件和库文件打包在一起，生成最终的可执行文件。

> **小知识**：大型工程通常先由编译器把各个文件单独编译成 `.o` 文件，再统一链接。这样修改了某个文件，只需重新编译那一个 `.o`，而不必全盘重编，极大提升了效率。

**gcc编译选项**
```bash
gcc [选项] 要编译的文件 [选项] [目标文件]
```

**多个文件：** 将全部 `.c` 打包成 `.o`
```bash
gcc code.o code1.o code2.o -o code
```

## 3.2 动态链接 vs 静态链接

- **静态链接（静态库 `.a`）**：把库代码直接“拷贝”进可执行文件。
    - 优点：运行快，不依赖外部环境。
    - 缺点：文件体积巨大，内存中会有多份重复代码，库更新了必须重新编译。
    
- **动态链接（动态库 `.so`）**：只记录库的地址，运行时由操作系统加载库。
    - 优点：文件小，节省内存和磁盘，库更新方便。
    - 缺点：如果运行环境缺失动态库，程序会直接崩溃（找不到 `.so`）。
    - 注：Linux 下动态库为 `.so` (Windows 为 `.dll`)

# 4. 自动化构建：Make 与 Makefile

如果一个项目有 100 个 `.c` 文件，每次改一个都要手敲 100 遍 `gcc` 吗？当然不！这就是 `make` 工具和 `Makefile` 文件的作用

## 4.1 Makefile 的核心规则

```shell
# Makefile

# 目标文件:依赖文件
myproc: myproc.c           # 可以是多个依赖文件
	gcc -o myproc myproc.c # 第二行必须以tap建为开头，以什么方式编译
```
_(⚠️注意：第二行必须用 Tab 键缩进，不能用空格！)_

当你执行 `make` 命令时，它会寻找当前目录下的 `Makefile`，并执行第一条规则

## 4.2 为什么不能多次执行 make

执行一次 `make` 生成 `myproc` 后，如果没修改过 `myproc.c`，再次 `make` 会提示 已是最新

- **原理**：`make` 会比较 **目标文件** 和 **依赖文件** 的修改时间。如果 `myproc.c`（依赖）比 `myproc`（目标）老，说明源码没改过，`make` 就会跳过编译以节省时间

## 4.3 伪目标 `.PHONY` 与清理规则

通常我们需要一个清理命令（`make clean`），为了防止目录下正好有个文件叫 `clean` 导致规则冲突，我们使用 `.PHONY` 声明它为**伪目标**，让它无视时间对比，永远被执行

```bash
# Makefile

myproc:myproc.c
	gcc -o myproc myproc.c

.PHONY:clean # .PHONY:修饰符  修饰 clean
clean:       # 依赖为空，语法规则一样
	rm -f myproc
```

```bash
# 命令行中执行，清除文件
make clean # 出现 rm -f myproc (也就是我们在 Makefile 中写入的 clean)
```

## 4.4 Makefile 定义变量

`Linux` 中的 `Makefile` 里定义变量与C语言中的宏定义很像，本质是替换。C语言的语法为 `#default`、`Linux` 中则为 `$()`
特殊语法：`$()` 替换内容、`$^` 表示依赖文件、`$@` 表示目标文件
```bash
# 定义的变量
BIN=proc.exe
CC=gcc
SRC=myproc.c
FLAGS=-o
RM=rm -f

# 替换$()
$(BIN):$(SRC)
$(CC) $(FLAGS) $@ $^ # $@ = BIN   $^ = SRC
.PHONY:
clean:
$(RM) $(BIN)

.PHONY:test
test:
@echo $(BIN)     # 输出 proc.exe
@echo $(CC)      # 输出 gcc
@echo $(SRC)     # 输出 myproc.c
@echo $(FLAGS)   # 输出 -o
@echo $(RM)      # 输出 rm -f
```


## 4.5 Makefile 进阶：变量与自动推导

在大型工程中，我们使用变量和通配符来简化编写：

- `$@`：代表目标文件名（如 `myproc`）
- `$^`：代表所有依赖文件名（如 `myproc.c`）
- `$<`：代表第一个依赖文件名
- `$(wildcard *.c)`：获取当前目录下所有的 `.c` 文件

```shell
# Makefile

BIN = proc.exe
CC = gcc
SRC = $(wildcard *.c)
OBJ = $(SRC:.c=.o)

$(BIN): $(OBJ)
	@$(CC) -o $@ $^
%.o: %.c
	@$(CC) -c $<

.PHONY: clean
clean:
	rm -f $(OBJ) $(BIN)
```

## 4.6 Makefile 扩展

### 1. Makefile 顺序问题

我们把上面写的 `Makefile` 拆解一番
```bash
# 第一个命令(make)
myproc:myproc.c
	gcc -o myproc myproc.c

.PHONY:clean # 伪目标

# 第二个命令(make clean)
clean:
	rm -f myproc
```
因为 `Makefile` 顺序问题，在执行 `make` 命令时，最先执行 `gcc -o myproc myproc.c`，只有明确告知需要用 `clean` 时，执行 `make clean` 才会执行 `rm -f myproc`

如果像下列这样写：
```bash
# 第一个命令(make)
clean:
	rm -f myproc

.PHONY:clean # 伪目标

# 第二个命令(make myproc)
myproc:myproc.c
	gcc -o myproc myproc.c
```
会因为顺序问题，执行 `make` 时就变成 `rm -f myproc`，**但我们都会把创建文件放在第一个**

### 3. Makefile 深层理解（推导过程）

>机器只能识别 `.o` 文件，那为什么 `Makefile` 文件中，可以写成 `myproc:myproc.c` 呢？

那是因为 Linux 中优化了 `Makefile`，省略了许多步骤，完整的路线图如下：
```bash
#myproc:myproc.c
#	gcc -o myproc myproc.c

myproc:myproc.o
gcc myproc.o -o myproc
myproc.o:myproc.s
gcc -c myproc.s -o myproc.o
myproc.s:myproc.i
gcc -S myproc.i -o myproc.s
myproc.i:myproc.c
gcc -E myproc.c -o myproc.i

.PHONY:clean
clean:
rm -f *.i *.s *.o myproc
```
- `myproc:myproc.o` 这里的 `myproc.o` 不存在，把 `myproc:myproc.o` 入栈
- `myproc.o:myproc.s` 这里的 `myproc.s` 不存在，把 `myproc.o:myproc.s` 入栈
- `myproc.s:myproc.i` 这里的 `myproc.i` 不存在，把 `myproc.s:myproc.i` 入栈
- `myproc.i:myproc.c` 这里的 `myproc.c` 存在，依次出栈并执行
- 从此就完成了从上到下入栈，从下到上执行的 `Makefile` 推导规则


### 4. 多文件 Makefile（手写链接）

多文件的 `Makefile` 写法 与  上述单文件的 `Makefile` 写法不同，如下：将多个文件编译成 `.o`，统一链接
```bash
BIN=proc.exe
CC=gcc
SRC=myproc.c
OBJ=myproc.o
LFLAGS=-o
FLAGS=-c
RM=rm -f

$(BIN):$(OBJ)
	$(CC) $(LFLAGS) $@ $^
%.o:%.c # 把当前路径下所有的 .o/.c 依次展开
	$(CC) $(LFLAGS) $< # 对源文件依次进行编译

.PHONY:clean
clean:
	$(RM) $(OBJ) $(BIN)
```

不想每次 `make` 和 `make clean` 打印命令，可以用 `@` 来注释掉
```bash
BIN=proc.exe
CC=gcc
SRC=myproc.c
OBJ=myproc.o
LFLAGS=-o
FLAGS=-c
RM=rm -f

$(BIN):$(OBJ)
	@(CC) $(LFLAGS) $@ $^
	@echo "linking ... $^ to $@"
%.o:%.c # 把当前路径下所有的 .o/.c 依次展开
	@$(CC) $(LFLAGS) $< # 对源文件依次进行编译
	@echo "compling ... $< to $@"

.PHONY:clean
clean:
	$(RM) $(OBJ) $(BIN)
```

### 5. 多文件 Makefile（自动链接）

每次使用 `Makefile` 都要自己去用 `.o` 文件链接，如果 `.o` 文件特别多，这就会失去 `Makefile` 文件的便利性，因此就有**自动链接**的语法
```bash
BIN=proc.exe
CC=gcc
# SRC=$(shell ls *.c)
SRC=$(wildcard *.c)   # 显示当前目录下所有的.c文件名
OBJ=$(SRC:.c=.o)      # SRC内部的文件名.c -> 文件名.o
LFLAGS=-o
FLAGS=-c
RM=rm -f

$(BIN):$(OBJ)
	@(CC) $(LFLAGS) $@ $^
	@echo "linking ... $^ to $@"
%.o:%.c # 把当前路径下所有的 .o/.c 依次展开
	@$(CC) $(LFLAGS) $< # 对源文件依次进行编译
	@echo "compling ... $< to $@"

.PHONY:clean
clean:
	$(RM) $(OBJ) $(BIN)
	
.PHONY:test
test:
	@echo $(SRC)
	@echo $(OBJ)
```

**对Makefile（自动链接）进行测试**
```bash
# 在lesson9中输入
count=1; while [ $count -le 100 ]; do touch code${count}.c; let count++; done
```
可以看到创建了 100 个 `.c` 文件，此时使用 `make` 和 `make clean` 时，就可以看到创建 `.o` 和 `链接` 的输出

# 5. 调试器：GDB 与 CGDB

写代码哪有不写出 Bug 的？`gdb` 是 Linux 下的命令行调试神器（`cgdb` 是它的可视化分屏升级版）

## 5.1 调试前提

默认 `gcc` 编译出的是 `release` 版本（无调试信息）。必须加 `-g` 选项生成 `debug` 版本：

```bash
gcc mycmd.c -o mycmd -g
cgdb mycmd   # 启动 cgdb 调试
```

| `until 行号`                | 执行到指定行号                       | `until 20`            |
| `info/i locals`           | 查看当前栈帧的局部变量值                  | `info locals`         |
| `watch 变量`                | 当跟踪值变化时，GDB辉暂停程序的执行           | `watch x`             |
| `b 文件名/行号/函数名 if i == 30` | 给断点加上条件，条件满足时执行断点             | `b 10 if i == 20`     |
| `condition 序号 i == 30`    | 给存在的断点加条件                     | `condition x i == 30` |
| `按Esc进入代码屏`/`按i退出`        | 进入代码屏，可以用滚轮滑动cgdb上显示的代码       | `按Esc进入代码屏`/`按i退出`    |

## 5.3 高级技巧：Watch 与 条件断点

- **`watch 变量`**：监控变量。当该变量的值发生改变时，程序会自动暂停。非常适合抓“变量莫名其妙被改变”的 Bug。
- **条件断点 `b [行号] if [条件]`**：比如 `b 9 if i == 30`。在循环了 1000 次的 `for` 循环里，你可以直接让程序在第 30 次循环时停下来，不用手动按 30 次 `continue`。
- **`set var 变量=值`**：在调试中动态修改变量的值，用来验证 Bug 是否由该变量引起。
