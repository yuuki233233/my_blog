# 1. 冯 · 诺依曼体系

在认识操作系统之前，必须先搞懂计算机的骨架。几乎所有的计算机都遵循冯·诺依曼体系：
- **输入设备**：键盘、鼠标
- **输出设备**：显示器、打印机
- **存储器**：内存
- **中央处理器**：CPU（包括运算器和控制器）

> **冯 · 诺依曼体系规则**：
> 1. **CPU** 只能与**内存**打交道，不能直接访问外设（数据层面）
> 2. 外设的数据只能写入内存、或者从内存中读取
> 3. 任何程序的运行，本质上都是数据在内存和 CPU 之间来回搬运

# 2. 操作系统的本质：管理

操作系统（OS）在整个计算机体系中处于承上启下的位置：
- **对上**：为用户程序提供良好的执行环境（目的）
- **对下**：管理所有的软硬件资源（手段）

![720](图片/操作系统.png)

>1. 软硬件体系结构为层状结构
>2. 访问操作系统，必须使用系统调用（系统提供的函数接口）
>3. 只要程序访问了硬件，必须贯穿整个软硬件体系结构
>4. 库可能在底层封装了系统调用

## 2.1 如何理解管理

贯穿了整个 Linux 系统中的思维模型是：**先描述，再组织**
例子：校长（OS）要管理全校的学生（硬件/进程）
1. **先描述**：校长不可能每天盯着学生，他会给每个学生建一份档案（用 `struct` 结构体记录身高、成绩等属性）
2. **再组织**：把所有学生的档案按照班级、学号，用链表或树等数据结构组织起来
3. **再增删查改**：校长开除一个学生，只需要在组织好的结构体里找到他的档案，删除即可

**结论**：操作系统对硬件的管理，本质上就是对**数据结构（结构体+链表等）的增删查改**

## 2.2 概念

操作系统是一款进行软硬件 **管理** 的软件，操作系统包括：
- 内核：进程管理，内存管理，文件管理，驱动管理
- 其他程序：函数库，shell程序等

# 3. 进程概念：什么是进程

程序是一个静态的、躺在磁盘上的可执行文件。而**进程是一个动态、正在内存中运行的程序**

>**终极公式**：
>**进程 = 内核数据结构（PCB）+ 自己的程序代码和数据**

### 3.1 进程形成与销毁过程

1. 执行 `.c` 文件，先存磁盘中
2. 需要使用时，将 `.c` 形成的**可执行代码和数据**放入内存里
3. 操作系统在内存中找到**可执行代码和数据**，并将其链接起来

代码演示
```c
// struct XXX -> 操作系统(PCB) -> struct task_struct{}
struct XXX
{
	// 代码地址
	// 数据地址
	// id
	// 优先级
	// 状态
	...
	struct XXX *next; // 将每一个进程链接起来，形成链表，方便增删查改
}
```

CPU 拿到进程去调度，找到对应的 PCB，通过 PCB 找到对应的的代码和数据。进程运行结束，在操作系统内将代码和数据释放掉，链表将结束的进程释放掉，此时操作系统完成了对进程的删除

### 3.2 描述进程： PCB 与 task_struct

在 Linux 中，用来描述进程的档案叫做 **task_struct**(也就是 **PCB**，进程控制块)。它包含了进程的：
- **标识符（PID）**：区别进程
- **状态**：运行、睡眠、停止、僵尸
- **优先级**：谁先被 CPU 处理
- **程序计数器（PC）**：下一条要执行的指令地址
- **上下文数据**：寄存器里保存的临时数据
- **内存指针**：指向该进程的代码、数据、内存块（`mm_struct`)
- **I/O状态信息**：显示I/O请求，分配给进程的I/O设备和被进程使用的文件列表
- **记账信息**：处理器时间总和，使用时钟数总和，时间限制，记账号

所有的 `task_struct` 在内核中通过**双向链表**组织起来，方便 OS 统一管理

### 3.3 组织进程：Linux双链表 vs 原始双链表

在操作系统中，所有进程的 PCB 用双链表链接起来

```
 —— —— —— —— —— —— —— —— —— —— —
|                               |
-> next -> next -> next -> next -
- prev <- prev <- prev <- prev <-
|                               |
 —— —— —— —— —— —— —— —— —— —— —
```

>[!note] 怎么理解进程放在双链表里 又 属于队列？
>1. 原始双链表：下一个节点指向结构体的开头（从上到下字节依次增大）
>2. Linux上的双链表：下一个节点的 list 指向下一个节点的 list

>[!warning] 问题：Linux上的双链表，怎么去访问结构体里面的任何一个成员?
在 `struct task_struct a`中，`&a == &a.x`，由于结构体中的数据从上到下字节依次增大，就可以用
>- **list 强转为0 -> list 地址 = 偏移量**（ `&((struct task_struct*)0->list)` ）
>- **结构体地址里 list 地址 - 偏移量 = 结构体头数据**（`list - &((struct task_struct*)0->list)` ）

如图二所示

## 4.1 运行和阻塞变化过程

- 运行：进程在**调度队列**中，进程状态都是running
- 阻塞：**硬件队列**中，等待某种硬件或资源就绪（键盘，显示器，网卡，磁盘...）
- 硬件队列：OS要管理系统中的各个硬件资源，每个硬件都有信息，并且需要用链表组织起来，方便对硬件状态进行管理

>[!note]
>- 运行 -> 阻塞：当输入 scanf函数 时，此时程序就停止下来
>- 阻塞 -> 运行：本质上就是找到 PCB，再把 PCB 链接到运行队列
>进程状态的变化，表现之一，就是要在不同的队列中进行流动。本质都是数据结构的增删查改！

## 4.2 进程的状态与生死
当内存不足时，操作系统会做一系列的交换算法，把相关的内存块（阻塞状态且没就绪的进程）交换到磁盘上，只将 PCB 保留下来，这样就可以节省空间。这种状态称为挂起状态。

- **R (Running)**：运行状态。（注意：只要在**运行队列**里，哪怕现在没被 CPU 执行，也算 R）
-  **S (Sleeping)**：可中断睡眠。（最常见，比如等待键盘输入 `scanf`，等待 `sleep`）
-  **D (Disk Sleep)**：不可中断睡眠。通常等待磁盘 IO，无法被 Ctrl+C 杀死
- **T (Stopped)**：停止状态。由 `SIGSTOP` 触发，可用 `SIGCONT` 恢复
* **X (Dead)**：死亡状态，瞬间状态，不可见

一个进程又多个状态，随着程序进行而发生变化，以下是状态在 Kernel 源代码的定义：
```c
/*
*The task state array is a strange "bitmap" of
*reasons to sleep. Thus "running" is zero, and
*you can test for combinations of others with
*simple bit tests.
*/
static const char* const task_state_array[] = {
	"R (running)", /*0 */
	"S (sleeping)", /*1 */
	"D (disk sleep)", /*2 */
	"T (stopped)", /*4 */
	"t (tracing stop)", /*8 */
	"X (dead)", /*16 */
	"Z (zombie)", /*32 */
};
```

### 1. 僵尸进程 (Zombie)

**现象**：子进程先退出，父进程还在运行，但父进程没有读取子进程的退出状态（没调用 `wait`）
**后果**：子进程的代码和数据释放了，但 **PCB（task_struct）一直保留着**，等待父进程回收。如何父进程一直不处理，就会造成**内存泄漏**

**代码演示**
```c
#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>

int main()
{
    pid_t id = fork();
    if(id == 0)
    {
        int count = 5;
        while(count)
        {
            printf("我是子进程，正在运行: %d\n", count);
            sleep(1);
            count--;
        }
    }
    else
    {
        while(1)
        {
            printf("我是父进程，正在运行...\n");
            sleep(1);
        }
    }

    return 0;
```

### 2. 孤儿进程 (Orphan)

**现象**：父进程先退出，子进程还在运行
**后果**：子进程失去父亲，会被 **1号进程（`init` 或 `systemd`）** 领养，**自动变成后台进程** `./[file] &`。孤儿进程会变成后台进程，不能用 `Ctrl+C` 杀掉，只能在另一台，用 `kill -9 [id]` 杀掉进程

**代码演示**
```c
#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>

int main()
{
    pid_t id = fork();
    if(id == 0)
    {
        while(count)
        {
            printf("我是子进程，pid: %d, ppid: %d\n", pid(), ppid());
            sleep(1);
        }
    }
    else
    {
        int count = 5;
        while(1)
        {
            printf("我是父进程，pid: %d\n", ppid());
            sleep(1);
            count--;
        }
    }

    return 0;
```

#### 1.1 fork 返回值

`fork()` 函数会创建一个子进程。它有一个极其特殊的现象：**调用一次，返回两次**
- 在父进程中，返回子进程的 PID > 0
- 在子进程中，return = 0
- 如果内存不足，return < 0

```bash
[zjh@izj6cd3zr5adf6jnm3mwihz lesson12]$ cat myprocess.c
#include <stdio.h>
#include <unistd.h>       // sleep
#include <sys/types.h>    // getpid子进程 getppid父进程

int main()
{
    printf("父进程开始运行,pid=%d\n", getpid());
    pid_t id = fork();
    if(id < 0)
    {
        perror("fork");
        return 1;
    }
    else if(id == 0)
    {
        // child
        while(1)
        {
            sleep(1);
            printf("我是一个子进程~, 我的pid: %d, 我的父进程id: %d\n", getpid(), getppid());
        }
    }
    else
    {
        // father
        while(1)
        {
            sleep(1);
            printf("进程开始运行,pid=%d\n", getpid());
        }
    }
    printf("进程开始运行,pid=%d\n", getpid());
    
    return 0;
}
```

`fork()` 之后，父子代码默认是共享的（写实拷贝），只是执行不同的代码块，父进程 `id=1`，子进程 `id=0`

为什么fork给父子返回各自不同的返回值？
在系统里父进程与子进程的比例为 `父 : 子 = 1 : n`，因为父进程有多个子进程，需要不同的id来区分子进程，方便对子进程做管理。

#### 1.2 为什么一个函数会返回两次

 类似于 `STL` 中的 `find()函数`，里面的返回下标，核心工作虽然做完了，但外层还需要进行返回对应下标的数据。`fork函数` 执行完了 `返回id`，继续返回到当前代码下一行，`fork()函数` 中申请新的 `pcb`、拷贝父进程 `pcb` 给子进程、`子进程pcb` 放入 `进程list`、在此子进程已经被创建，甚至被调度。所以实际上，在 `return` 之前，父子就已经被返回了（return 也是一条语句）

**为什么有两个返回值？**
因为 `fork` 之后，父子进程共享代码，但执行流分叉了。父进程需要子进程的 ID 去管理它，子进程可以通过返回值 0 知道自己是被创建出来的

### 优先级 (PRI) 与 Nice (NI)

CPU 资源极少，而进程极多（竞争性）。为了让重要进程先执行，有了优先级
- **PRI**：进程真正的优先级，**数值越小，优先级越高**
- **NI**：Nice 值（修正数据），范围是 `[-20, 19]`，共 40 个级别
- **公式**：`PRI(new) = PRI(old) + NI`

因为优先级设立不合理，会导致优先级低的进程，长时间得不到 CPU 资源，进而导致：进程饥饿

### 进程竞争、独立、并行、并发

- 竞争性：硬件是少数的，而**进程是多数的**，使用资源的进程之间，必然是竞争关系，所以就有了**优先级和权限**的概念
- 独立性：进程 = PCB（内核数据结构） + 代码和数据，进程运行需要独享各种资源，多进程运行期间互不干扰。（VS2022崩溃了，对Github没有影响）
- **并行**：多个 CPU 核心真正同时运行多个进程
- **并发**：一个 CPU 通过时间片轮转，在多个进程间极速切换，宏观上看起来像同时运行

## 进程切换的底层

### 普通程序与死循环进程如何运行
- 一个进程占有 CPU，不会把自己的代码跑完（时间片）
- 死循环进程，不会一直占有 CPU，而是通过时间片，多进程互相切换，这与上面的进程并发一样

>**寄存器**是 CPU 内部临时存数据的地方。当进程 A 的时间片用完，OS 会把 CPU 寄存器里 A 的数据（硬件上下文）全拷贝出来，保存到 A 的 `task_struct` 里；然后把 B 的数据加载进寄存器。这就是**上下文切换**。

### CPU 与 寄存器
CPU 里面存在非常多的寄存器，每个寄存器都有不同的功能，**寄存器**是用来保存当前**数据的临时数据**
- 寄存器就是 CPU 内部的临时空间
- 寄存器（空间） != 寄存器里面的数据（内容）

![](图片/进程切换.png)

- 寄存器内部都会保留数据（硬件上下文数据）。进程A因为时间片的原因需要切走，进程A切走前，将寄存器里的数据拷贝一份给自己。`[假设进程A运行到了第50行代码]`
- 把进程B放进来，此时进程B的数据将寄存器里的数据覆盖。运行一段时间，进程B因为时间片需要切走，拷贝一份寄存器内的数据给自己，再切换成进程A `[进程A第50行代码继续运行]`
- 进程切换本质：保存和恢复当前进程的硬件上下文的数据，即 CPU 内寄存器的内容

>注意：
>时间片：当代计算机都是分时操作系统，没有进程都有它合适的时间片。时间片到达，进程就被操作系统从CPU中脱离下来

## Linux 2.6 的 O(1) 调度算法

下面是Linux2.6内核中进程队列的数据结构
![](图片/queue[140].png)

分时操作系统：基于时间片，在时间内的进程执行完，才到下一个进程执行
实时操作系统：操作系统接管，与优先级有关，优先级越高越先执行

*   `runqueue` 中有一个 `queue[140]` 数组，**数组下标对应优先级**
	* 实时操作系统优先级[0, 99]（不关心）
	* 分时操作系统优先级[100, 140]（nice取值范围）
*   如何快速找到最高优先级的进程？用 **`bitmap[5]`**（5个32位整型，刚好160位，代表140个队列是否为空）。通过位运算瞬间定位
*   **防饥饿机制**：设计了 `active`（活跃队列，时间片没用完的）和 `expired`（过期队列，时间片用完的）。等 active 全跑完，直接交换两个指针，瞬间开始新一轮

### 活动队列

- **queue[140]**：一个元素就是一个进程队列，相同优先级的进程按照FIFO规则进程排队调度，所以，数组下标就是优先级
- 时间片还没有结束的所有进程，都按照优先级放在该队列的对应队列（queue[ ]）
- 从该结构中，选择一个最合适的进程，过程是什么样的？
	1. 从 0 下标开始遍历 `queue[140]`
	2. 找到第一个非空队列，此队列优先级最高
	3. 拿到选中队列的第一个进程，开始运行并调度
	4. 遍历 `queue[140]` 需要一个一个遍历，效率低
- **unsigned int bitmap[5]** 位图：
	- 一共 140 个优先级，一共140个进程队列，为了提高查找非空队列的效率，用 `5 * 32` 个比特位表示队列是否为空，这样就可以提高查找效率
	- 为什么 `bitmap[ ]` 中用 5，因为 `unsigned int = 32 byte、bitmap[5] = 5，unsigned int bitmap[5] 为 160 byte`，每一个字节对应一个优先。如果是 4 的话，就只有 128 个优先级（少了）、如果是 6 话，就有192个优先级（多了）。
- **nr_active**：总共有多少个运行状态的进程

调度过程：
在调度时，先查 `nr_active`，大于 0，再查 `bitmap[]`，确认下标，直接索引 `queue[]` 并找到目标队列，再从头部移除，把对应的节点拿出来，把对应节点的 PCB 拷贝放入到 `current` 指针里，执行切换算法，然后再把 `current` 指针放到 CPU 上，就可以调度了

### 过期队列

#### 进程饥饿

进程饥饿：当有个进程的优先级为60，且一直循环执行，当执行完这个进程，进程需重新放入`runqueue` 里的 `queue[]`，从尾开始接。这就导致了这个进程一直死循环，进到导致后面优先级低的进程执不到，造成进程饥饿（如何解决）

为解决进程饥饿问题，可以设计两个队列，一个是活跃进程，一个是过期进程

#### active指针 与 expired指针

- active：指向 array[0] 活跃进程
- expired：指向 array[1] 过期进程

在调度过程中，先调度 active 指向的优先级高的进程，在 CPU 调用完的进程不再访问 active指针，而是访问 expired指针 脱离到过期进程。活跃进程越来越少，脱离到过期进程的越来越多，这就能保证活跃进程的全部进程执行完，制止了进程饥饿而导致的死循环问题。

活跃进程里全部进程调度完毕，用 swap(&active, &expired) 交换数据，程序又可以继续进行

## 虚拟地址

为什么父进程与子进程地址是一模一样的，首先可以理解子进程是对父进程进行了浅拷贝，父子并没有对变量进行任何修改。来一段代码进行演示：
```c
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>

int g_val = 100;
int main() {
    pid_t id = fork();
    if (id == 0) {
        g_val = 200; // 子进程修改
        printf("child: %d, addr: %p\n", g_val, &g_val);
    } else {
        sleep(1); // 父进程等子进程跑完再读
        printf("parent: %d, addr: %p\n", g_val, &g_val);
    }
}
// 输出结果：
// child: 200, addr: 0x60103c
// parent: 100, addr: 0x60103c
```

**灵魂拷问**：为什么地址一模一样（`0x60103c`），但变量的值却不一样（一个200，一个100）？难道同一个地址存了两个值？

**答案**：你在 C/C++ 里看到的、打印出来的所有地址，**全是虚拟地址！** 物理地址被 OS 藏起来了，用户根本看不到

## 进程地址空间 (mm_struct)

更详细的说，程序地址空间应当改为**进程地址空间**，如下图是一个进程的地址空间
![](图片/进程地址空间.png)

从图中总结到的信息：
- 父子进程各有自己的 地址空间（mm_struct）和 页表
- 页表（利用哈希映射）
	- 父进程：左为虚拟地址，右为物理内存
	- 子进程：左为物理内存，右为虚拟地址
	- 虚拟地址和物理内存可以互相访问
- 父进程的页表右指向物理内存，子进程的页表左指向物理内存

父进程 创建 若干个子进程，子进程对父进程的虚拟地址和页表进行浅拷贝，为什么子进程修改内容时，父进程却没有改变？
- 回到那个现象：`fork()` 子进程时，OS 采用了**写时拷贝 (Copy-On-Write)** 技术。父子进程一开始共享物理内存，但只要子进程试图修改 `g_val`，OS 立刻在物理内存重新复制一份，让子进程的页表指向新的物理内存。因此，**虚拟地址不变，物理地址变了**
- 由于父子进程的内容不一样，所以返回的内容也不一样。即一个变量，即 == 0 又 > 0，导致 if else 进入不同类域中

## 为什么要有虚拟地址空间？

用户不能直接访问物理内存，单可访问虚拟内存，当物理内存占 100 字节是，在虚拟内存空间开辟 100 字节，通过页表映射，就可访问物理内存

1. **安全风险**：恶意程序可以随便改别人的内存，直接让系统瘫痪。有了虚拟地址，OS 可以通过页表检查你的权限（比如拦截野指针）
    
2. **地址不确定**：每次程序加载物理内存的位置都不一样。有了虚拟地址，每个程序都以为自己是从 `0x400000` 开始跑的，编译器不用重新编译
    
3. **效率低下**：内存不够时，OS 可以将部分内存换出到磁盘，程序仍以为自己在连续的内存中，这叫**解耦**

## 如何对虚拟内存进行管理

描述 Linux 下进程的地址空间的所有的信息的结构体是 mm_struct。每一个进程只有一个 mm_struct 结构，在每一个进程的 task_struct 结构中，有一个指向该进程的 mm_struct 结构体指针
```c
struct task_struct
{
	struct mm_struct *mm; // 对普通用户来说，该字段指向虚拟地址空间的用户空间部分，对内核线程这部分为NULL
	struct mm_struct *active_mm; // 内核线程使用。如果该进程是内核线程，它的 mm 字段为 NULL，表示没有内存地址空间，也不一定，这是因为所有进程关于内核的映射都是一样的，内核线程可以使用任意进程的地址空间
	
	/*...*/
}
```

可以说，`mm_struct` 结构是对整个用户的描述。每一个进程都会有自己独立的 `mm_struct` 才能互不干扰。`task_struct` 到 `mm_struct` 进程的地址空间的分布情况：
![](图片/task_struct到mm_struct分布情况.png)

每一个进程都有自己的 `mm_struct`，操作系统会将多个进程的 `mm_struct` 组织起来，组织成链表，方便对虚拟地址的增删查改。虚拟空间的组织方式有两种：
- 当虚拟区较少，采取单链表，有 mmap 指针指向这个链表
- 当虚拟区多是采取红黑树进行管理，有 mm_rb 指向这棵树

`Linux` 内核使用 `vm_area_struct` 结构来表示一个独立的虚拟内存区域（VMA），由于每一个不同质的虚拟内存区域功能和内部机制都不同，因此一个进程使用多个 `vm_area_struct` 结构来分别表示不同类型的虚拟内存区域。上面的两种组织方式就是使用 `vm_area_struct` 结构来连接各个 VMA，方便进程快速访问。
```c
struct vm_area_struct {
	unsigned long vm_start; //虚存区起始
	unsigned long vm_end; //虚存区结束
	struct vm_area_struct *vm_next, *vm_prev; //前后指针
	struct rb_node vm_rb; //红⿊树中的位置
	unsigned long rb_subtree_gap;
	struct mm_struct *vm_mm; //所属的 mm_struct
	pgprot_t vm_page_prot;
	unsigned long vm_flags; //标志位
	struct {
	struct rb_node rb;
	unsigned long rb_subtree_last;
	} shared;
	struct list_head anon_vma_chain;
	struct anon_vma *anon_vma;
	const struct vm_operations_struct *vm_ops; //vma对应的实际操作
	unsigned long vm_pgoff; //⽂件映射偏移量
	struct file * vm_file; //映射的⽂件
	void * vm_private_data; //私有数据
	atomic_long_t swap_readahead_info;

#ifndef CONFIG_MMU
	struct vm_region *vm_region; /* NOMMU mapping region */
#endif
#ifdef CONFIG_NUMA
	struct mempolicy *vm_policy; /* NUMA policy for the VMA */
#endif
	struct vm_userfaultfd_ctx vm_userfaultfd_ctx;
} __randomize_layout;
```
